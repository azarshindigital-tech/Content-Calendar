# مناسبت‌یار — تقویم هوشمند مناسبت‌ها و دستیار تولید محتوا

یک وب‌اپ کامل برای مرور **مناسبت‌های سال ۱۴۰۵** (تقویم شمسی/میلادی با نماهای روز، هفته و ماه)
به‌همراه یک **دستیار هوش مصنوعی** که مناسبت‌های هفت روز آیندهٔ مرتبط با یک کسب‌وکار را پیدا
می‌کند و برای هرکدام ایدهٔ محتوایی اجرایی می‌سازد.

- فرانت‌اند: HTML/CSS/JavaScript ماژولار و بدون بیلد (بدون فریم‌ورک، RTL، فونت Vazirmatn).
- بک‌اند: یک **Cloudflare Pages Function** که به‌صورت امن و سمت سرور با **Google Gemini** کار می‌کند.
- منبع داده: `public/data/events.json` — تنها مرجع معتبر تقویم (۱۲۳۶ مناسبت).

---

## ۱. پیش‌نیازها

- Node.js نسخهٔ ۱۸ یا بالاتر (با نسخهٔ ۲۲ تست شده).
- یک کلید معتبر **Google Gemini API**.
- برای انتشار: یک حساب **Cloudflare** و ابزار `wrangler` (به‌عنوان وابستگی توسعه نصب می‌شود).

## ۲. نصب وابستگی‌ها

```bash
npm install
```

تنها وابستگی، `wrangler` (برای اجرای محلی و انتشار) است. خودِ اپ در زمان اجرا هیچ
وابستگی npm ندارد؛ الگوریتم تبدیل تقویم (jalaali-js) به‌صورت ماژول داخلی در
`public/assets/js/vendor/jalaali.js` قرار دارد و هم فرانت‌اند و هم تابع سرور از همان استفاده می‌کنند.

## ۳. تنظیم کلید محرمانه برای توسعهٔ محلی

فایل نمونه را کپی کنید و کلید خود را در آن بگذارید:

```bash
cp .dev.vars.example .dev.vars
```

سپس در `.dev.vars` مقدار کلید را قرار دهید:

```
GEMINI_API_KEY=کلید-واقعی-شما
```

> `.dev.vars` در `.gitignore` قرار دارد و **هرگز** کامیت یا منتشر نمی‌شود.

## ۴. اجرای محیط توسعه

```bash
npm run dev
```

این دستور `wrangler pages dev` را اجرا می‌کند که هم فایل‌های استاتیک (`public/`) و هم
تابع `functions/api/suggest.js` را به‌صورت محلی سرو می‌کند. آدرس پیش‌فرض:
`http://127.0.0.1:8788`.

## ۵. اجرای تست‌ها

```bash
npm test
```

تست‌های `node --test` منطق تقویم و داده را پوشش می‌دهند:
- درستیِ تبدیل شمسی/میلادی (نوروز ۱۴۰۵/۰۱/۰۱ ↔ ۲۰۲۶-۰۳-۲۱، کبیسه‌نبودن ۱۴۰۵).
- صحت هر ۱۲۳۶ رکورد و **صفر مغایرت** بین تاریخ شمسی و میلادیِ ذخیره‌شده.
- استخراج دقیق بازهٔ هفت‌روزه و شناسه‌های پایدار رویدادها.

## ۶. ساختار پروژه

```
.
├── public/                         # دارایی‌های استاتیک (همین پوشه روی Cloudflare منتشر می‌شود)
│   ├── index.html                  # پوستهٔ تک‌صفحه‌ای اپ
│   ├── _headers                    # هدرهای امنیتی (CSP و ...)
│   ├── data/events.json            # دادهٔ مناسبت‌ها (منبع معتبر)
│   └── assets/
│       ├── css/{tokens.css, app.css}
│       └── js/
│           ├── vendor/jalaali.js   # الگوریتم تبدیل تقویم (MIT)
│           ├── calendar.js         # مدل تاریخ (JDN به‌عنوان مبنای واحد)
│           ├── data.js             # بارگذاری/اعتبارسنجی/ایندکس داده
│           ├── categorize.js       # دسته‌بندی نمایشی مناسبت‌ها
│           ├── icons.js            # آیکون‌های SVG
│           ├── ui-calendar.js      # رندر تقویم و فهرست
│           ├── ui-assistant.js     # رندر فرم و کارت‌های پیشنهاد
│           ├── api.js              # کلاینت فراخوانی API
│           └── app.js              # وضعیت و هماهنگی کل اپ
├── functions/
│   ├── api/suggest.js              # POST /api/suggest (منطق سرور)
│   └── lib/{gemini.js, prompt.js}  # لایهٔ تماس با مدل و ساخت پرامپت
├── tests/                          # تست‌های واحد (node --test)
├── wrangler.toml                   # پیکربندی Cloudflare Pages
├── .dev.vars(.example)             # کلید محرمانهٔ محلی
└── package.json
```

### معماری کلیدی

- **یک روز = یک عدد (JDN).** نمایش شمسی و میلادی صرفاً دو نمای یک روزِ واحدند، بنابراین
  تغییر نوع تقویم هرگز کاربر را به روز دیگری نمی‌برد.
- **ضدِ توهم‌زایی هوش مصنوعی.** تابع سرور بازهٔ هفت‌روزه را خودش محاسبه و مناسبت‌های
  واقعی را از داده استخراج می‌کند و فقط آن‌ها را به مدل می‌دهد. خروجی مدل بر اساس
  `occasionId` اعتبارسنجی می‌شود؛ **نام و تاریخ هر مناسبت از داده گرفته می‌شود، نه از مدل**،
  و هر پیشنهادی که به یک مناسبت واقعی گره نخورده باشد حذف می‌شود.

## ۷. ساختار مورد انتظار فایل JSON

آرایه‌ای از اشیاء با این سه فیلد:

```json
[
  { "name": "جشن نوروز/جشن سال نو", "shamsi_date": "1405/01/01", "gregorian_date": "2026-03-21" }
]
```

- `name` (string): نام مناسبت.
- `shamsi_date` (string): `YYYY/MM/DD` شمسی.
- `gregorian_date` (string): `YYYY-MM-DD` میلادی.

چند مناسبت در یک روز و نام‌های تکراری در تاریخ‌های مختلف پشتیبانی می‌شوند و حذف نمی‌شوند.

---

## ۸. تنظیمات مدل هوش مصنوعی و متغیرهای محیطی

| متغیر | نوع | پیش‌فرض | توضیح |
|---|---|---|---|
| `GEMINI_API_KEY` | **Secret** | — | کلید Gemini (الزامی). فقط سمت سرور استفاده می‌شود. |
| `GEMINI_MODEL` | متغیر عمومی | `gemini-3.8-flash` | نام مدل؛ بدون تغییر کد قابل تعویض است. |
| `APP_TIMEZONE` | متغیر عمومی | `Asia/Tehran` | منطقهٔ زمانی مبنای «امروز» و بازهٔ هفت‌روزه. |

متغیرهای عمومی در `wrangler.toml` تعریف شده‌اند. کلید محرمانه هیچ‌گاه در `wrangler.toml`،
کد فرانت‌اند، مخزن یا لاگ‌ها قرار نمی‌گیرد.

## ۹. ساخت و انتشار روی Cloudflare Pages

نیازی به مرحلهٔ Build نیست؛ خروجی همان پوشهٔ `public/` است و توابع از `functions/` خوانده می‌شوند.

### الف) انتشار از خط فرمان

```bash
# ۱) ورود به حساب Cloudflare
npx wrangler login

# ۲) ثبت کلید محرمانه روی محیط Production (مقدار به‌صورت تعاملی پرسیده می‌شود)
npx wrangler pages secret put GEMINI_API_KEY

# ۳) انتشار
npm run deploy      # معادل: wrangler pages deploy
```

نخستین انتشار، پروژهٔ Pages را می‌سازد و یک آدرس پیش‌فرض
`https://<project>.pages.dev` می‌دهد.

### ب) انتشار از طریق مخزن Git (اختیاری)

در داشبورد Cloudflare → Pages → اتصال مخزن، با تنظیمات:
- **Build command:** خالی
- **Build output directory:** `public`
- در بخش **Settings → Variables and Secrets**: افزودن `GEMINI_API_KEY` به‌عنوان Secret
  و در صورت نیاز `GEMINI_MODEL` / `APP_TIMEZONE`.

### بررسی نسخهٔ منتشرشده

1. باز کردن آدرس `*.pages.dev` و بررسی بارگذاری تقویم و شمارش ۱۲۳۶ مناسبت.
2. تست یک درخواست پیشنهاد:
   ```bash
   curl -s -X POST https://<project>.pages.dev/api/suggest \
     -H "Content-Type: application/json" \
     -d '{"business":{"field":"نرم‌افزار حسابداری ابری","product":"حسابداری","audience":"مدیران مالی","goals":["افزایش تعامل"],"channels":["لینکدین"]}}'
   ```
   خروجی موفق شامل `"ok":true` و آرایهٔ `eventSuggestions` است.

## ۱۰. امنیت

- کلید فقط در Secrets سمت سرور نگهداری می‌شود و هرگز به کلاینت یا لاگ نمی‌رود.
- اعتبارسنجی ورودی هم در کلاینت و هم در سرور انجام می‌شود؛ طول ورودی‌ها محدود شده است.
- فراخوانی مدل فقط از سمت سرور انجام می‌شود؛ پیام‌های خطا فارسی و بدون افشای جزئیات فنی‌اند.
- هدرهای امنیتی (از جمله Content-Security-Policy) در `public/_headers` تنظیم شده‌اند.
- کنترل درخواست‌های تکراری: دکمهٔ تولید هنگام پردازش غیرفعال می‌شود و درخواست قبلی لغو می‌گردد.

## ۱۱. محدودیت‌های شناخته‌شده

- **دامنهٔ داده:** فقط سال ۱۴۰۵ (۲۱ مارس ۲۰۲۶ تا ۲۰ مارس ۲۰۲۷). خارج از این بازه پیام مناسب نشان داده می‌شود.
- **دسته‌بندی مناسبت‌ها** بر پایهٔ کلیدواژه و صرفاً برای کمک به مرور است؛ ممکن است همهٔ موارد دقیق نباشند (نام و تاریخ هرگز تغییر نمی‌کنند).
- **فونت** از Google Fonts بارگذاری می‌شود؛ برای اطمینان بیشتر می‌توان Vazirmatn را محلی میزبانی کرد.
- **Rate limiting سمت سرور** در حد محدودسازی طول ورودی است؛ برای محیط پرترافیک، استفاده از Cloudflare Rate Limiting یا KV توصیه می‌شود.
- در نبود دسترسی شبکه یا شلوغ‌بودن موقت مدل، خطای قابل‌فهم نمایش داده می‌شود و امکان «تلاش دوباره» هست.
